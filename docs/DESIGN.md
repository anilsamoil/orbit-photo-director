# Design: Orbit Photo Director — map.astroanil.dev

## Problem Statement

For your 8 months on the ISS, build a tool that turns the question **"should I shoot now?"** into a glanceable answer. The website map.astroanil.dev publishes a ranked shot queue: which targets are about to be under the ISS, what the lighting regime is, what the cloud cover probability is, and how confident the score is. The map exists as context for the queue, not the other way around.

The Mac stays on Earth and runs unattended for the duration of the mission, publishing static updates. ISS-side, you just open a URL on a crew device — no install, no app, no orbit-side dependencies.

## What Makes This Cool

This is the inverted ISS tracker. Every existing tool — matteason's 3D tracker (https://github.com/matteason/live-cloud-maps), Spot the Station, Orbital Radar, ISS Detector — serves *ground viewers* aiming up: "when can I see ISS pass overhead?" None show the astronaut what's about to be under them and whether it's worth raising the camera. Same data sources, ~10-person target audience, completely different UX. You're building a tool that fits ten people in the world, and one of them is you.

## Constraints

- Mac stays on Earth, runs unattended for ~8 months (same operational pattern as your existing OpenClaw setup)
- ISS-side: just a browser opening map.astroanil.dev; ISS bandwidth is precious — page must be KB-scale, not MB-scale
- Pushing fixes from orbit is hard or impossible
- Site must be static (no server runtime to maintain, no certs to renew)
- Failures must be loud and obvious, never silent
- The user (you) is in orbit and will not be debugging this — the system either works or it visibly does not

## Premises (agreed)

1. **Killer feature is "should I shoot now?"** — a glanceable shot queue, top 5 cards in next 90 min.
2. **V1 cloud cover is observed, not forecast.** Geostationary IR/visible composite, 10-30 min refresh; NOAA SatCORPS hourly global composite as the primary V1 source.
3. **Lighting determines the *kind* of shot, not whether it's shootable. Cloud cover is a probabilistic confidence band, not a binary threshold.** Each pass scores: lighting regime tag (day / night / terminator / civil-twilight) + `P(unobstructed)` (0-100, used everywhere as 0-100) + dominant obstruction class — V1 uses three classes only: `clear`, `cloudy`, `sun-glint risk`. Thin cirrus / haze / snow-IR detection is V2 (real classifier work, doesn't fit a weekend). **V1 calibration is log-only** — Shoot/Skip + an outcome rating from the calibration form get persisted; threshold *tuning* is V2 work that needs N≥100 labeled samples to be meaningful.
4. **Reuse aggressively.** `sgp4` Python (orbit propagation, Mac-side only — single SGP4 implementation), MapLibre (map render), NOAA SatCORPS (clouds), OpenClaw daemon.py reliability pattern, Cloudflare **R2 + Workers** (deploy). Custom code is reserved for: scoring engine, shot-queue UX, ground-track-aware overlay.
5. **Mac runs the OpenClaw reliability pattern.** Watchdog, stall detection, retry with backoff, graceful staleness. The subprocess-wedge mitigations from your daemon.py work here directly — same recurring failure mode, same 10-min cap.
6. **Static, KB-scale site.** Mac generates pre-computed JSON (next 6h passes, scores, ground track polylines) plus a thin MapLibre client. No server.
7. **Graceful staleness over 500s.** A `STALE — last updated 4h ago` banner is better than a broken page. Site never goes down even if the generator does.
8. **8-month unattended Mac will fail at some point.** macOS updates, power loss, network blips, upstream API changes. Design for it. Earth-side monitoring (reuse OpenClaw notification pipeline) pings the public site every 5 min and alerts on staleness.

## Cross-Model Perspective

Codex (independent cold read, did not see this conversation) reframed and challenged:

- **Reframe (adopted):** the product is the **shot queue**, not the map. Codex called it an "orbit photo director" — the map is secondary; the real product is a mission-control shot list for someone floating past Earth at 7.7 km/s. Cards: target name, countdown, P(unobstructed), regime, "why this is worth shooting."
- **Challenge to Premise 3 (adopted):** "Clear sky" is not binary from orbit. Thin cirrus, smoke, haze, sunglint, snow/ice in IR, cloud parallax all break a single-number model. Cloud score must use confidence bands. Calibration: compare predicted-clear vs. actual-shot-quality for 20-50 shots and tune.
- **50% baseline (confirmed):** matteason/live-cloud-maps proves the data plumbing works; the missing 50% is the astronaut inversion — target DB, scoring, lighting regime, shot-queue UX, static JSON pipeline, stale-data behavior, ISS-bandwidth-friendly client, 8-month reliability.
- **Codex's V1 skip-list (incorporated):** cloud forecast, push alerts, camera/lens recommendations, attitude/window constraints, perfect cloud classification, offline ISS client, 3D globe, account system.

## Approaches Considered

### Approach A: Fork matteason, bolt on targets
Take matteason/live-cloud-maps as foundation; add saved targets as a layer; per-target hover with next-pass time and simple cloud %. Effort: S (1 weekend). Risk: Low. Reuses everything from matteason.

Rejected because it ships the wrong product — map-centric, no shot queue, no confidence bands, no lighting regimes. Likely thrown away as soon as B is built.

### Approach B: Greenfield Orbit Photo Director — V1 (recommended)
New codebase. Mac-side Python generator. NOAA SatCORPS for cloud composites. `sgp4` (Python) for orbit propagation; pass times pre-computed on the Mac, not in the browser. MapLibre for the map. Shot queue is primary view; map is context.

**Effort breakdown** (human scale; CC scale is much shorter):
- Build: ~3 weekends (scaffold/MapLibre, generator + scoring, calibration + reliability harness)
- Soak: 2 weeks of unattended runtime, mostly hands-off
- Freeze + runbook: ~1 day

Risk: Medium.

### Approach C: Unified V1+V2 — observed and forecast in one model
Same as B but cloud layer is unified: every score is `P(unobstructed) at time T` where T can be now (observed) or +12h (GFS forecast). Timeline slider on the frontend. Effort: L (4-6 weekends). Risk: Medium-High.

Rejected for V1 because forecast cloud (especially cirrus prediction) is its own bog and risks not shipping V1 in time. Reserved as the V2 architecture — V1's data model is forward-compatible.

## Recommended Approach: B — Greenfield V1

### Architecture

```
│                            │  sync   │  + Worker for        │  +      │                        │
│  python generator (10min)  ├────────►│    /api/log endpoint │ Worker  │  shot queue cards      │
│  + daemon.py watchdog      │  every  │  + custom domain     │  POST   │  + map (secondary)     │
│  + OpenClaw notify pipe    │  10 min │  map.astroanil.dev   │         │  + localStorage cache  │
└────────────────────────────┘         └──────────────────────┘         └────────────────────────┘
       ▲                                       ▲                                  │
       │  fetch TLE,                           │  cron-pulls calibration log,     │ Shoot/Skip/rate
       │  fetch cloud composite                │  /status.json health check       │  → POST /api/log
       │  (cached on Mac)                      │     (UptimeRobot free tier)      │  (Worker → R2)
       └───────────────────────────────────────┴──────────────────────────────────┘
```

### Components

**1. Earth-side generator** (`generator/main.py`)
- Tick: every **30 min** (revised from 10 min per /plan-eng-review 4A — cloud composite refreshes hourly, TLE refreshes 2-3×/day; 30 min is the right granularity and cuts resource use 3x)
- Steps per tick:
  1. Fetch latest ISS TLE from Celestrak (`stations.txt`). Cap at 1×/hour with on-disk cache; respect Celestrak ToS.
     - **TLE freshness policy**: warn at 24h since epoch; downrank `P(unobstructed)` confidence by 10% for every 12h past 24h; flag any pass after a detected reboost (epoch jump where mean motion changes by >0.005 rev/day) as `post-maneuver — re-fetch TLE before trusting`.
  2. Fetch latest NOAA SatCORPS global cloud composite if cached copy is >55 min old. SatCORPS is published as hourly NetCDF/HDF files, not a REST API — generator uses `xarray` + `netCDF4` to open and sample lat/lon. Single global file is ~100-200 MB/hour; fetch once per hour, cache locally, sample N targets from cache.
     - **Fallback path** (decide pre-launch): if SatCORPS access turns out to be flaky, switch to per-region geostationary stitching (GOES via NOAA NESDIS S3 + Himawari via JAXA + Meteosat via EUMETSAT). More code, no rate-limit risk. Spike SatCORPS in week 1 of implementation; if painful, switch immediately rather than discovering it in week 6.
  3. Load target DB (JSON in repo)
  4. Compute next 6h of passes for each target using `sgp4` (Python). All pass times pre-computed on the Mac. Frontend does NOT re-propagate — it just renders the JSON. Single SGP4 implementation.
  5. Score each pass: lighting regime, `P(unobstructed)`, obstruction class, regime fit, priority, nadir proximity. All score components written into the JSON for transparency.
  6. Write artifacts to versioned subfolder `out/v/{tick_ts}/`: `passes.json`, `track.json`, `status.json`, `iss_polynomial.json` (next-30-min ISS lat/lon polynomial fit for frontend live-position rendering), `cloud_tile.png`. Then write `out/manifest.json` containing every artifact's path + version + freshness fields:
     ```json
     {
       "version": "{tick_ts}",
       "generated_at": "2026-05-02T22:30:00Z",
       "tle_epoch": "2026-05-02T18:00:00Z",
       "cloud_composite_hour": "2026-05-02T22:00:00Z",
       "target_data_version": "v17",
       "build_version": "v1.3.2",
       "freshness": { "tle_hours": 4.5, "cloud_hours": 0.5, "ok": true },
       "artifacts": {
         "passes": "v/{tick_ts}/passes.json",
         "track": "v/{tick_ts}/track.json",
         "status": "v/{tick_ts}/status.json",
         "iss_polynomial": "v/{tick_ts}/iss_polynomial.json",
         "cloud_tile": "v/{tick_ts}/cloud_tile.png"
       }
     }
     ```
     Manifest is the SINGLE SOURCE OF TRUTH. Frontend reads `manifest.json` first, then loads every artifact from the version-tagged path inside. Mixed-version reads are impossible by construction.
  7. **Deploy via `rclone sync` to Cloudflare R2.** Not git push. Not Cloudflare Pages. R2 has a generous free tier (10GB storage, 1M Class A ops/month, 10M Class B/month) and no build-step counter. Custom domain map.astroanil.dev points to the R2 bucket via Cloudflare DNS. Each tick is `rclone sync out/v/ r2:map-astroanil-dev/v/` (writes versioned artifacts) followed by `rclone copyto out/manifest.json r2:map-astroanil-dev/manifest.json` (atomic pointer swap last). Cleanup script every tick deletes versions older than 1h from R2.
- Reliability: wrap subprocess calls in the OpenClaw daemon.py stall watchdog (10-min hard cap). Retry on transient failures with exponential backoff (max 1h). Structured JSON logs for post-mortem.
- **Log retention**: rotate generator logs daily; keep last 30 days; gzip and offload older to a `logs/archive/` dir if you care to keep them. Caps disk usage at <500 MB.
- **Secrets**: NASA Earthdata creds + Cloudflare R2 credentials live in `~/.config/orbit-photo-director/credentials.json` (mode 600). Earthdata tokens expire periodically — set a cron-checked expiry alarm 7 days before token expiry; rotation requires manual login (one-time pre-launch chore plus a documented runbook for the ground-side support contact).
- Status: every successful tick writes `last_run` timestamp + tick duration + per-step status to `status.json`.

**2. Cloud-data adapter** (`generator/cloud.py`)
- **V1 source**: NOAA SatCORPS global cloud composite (3km, hourly NetCDF). Fetch once per hour to local disk; sample lat/lon out of the cached file using `xarray`. Memory budget: a single hour of SatCORPS opened with chunked reads stays under ~500 MB resident.
- For each target lat/lon at predicted pass time: sample local cloud fraction → derive `P(unobstructed)` (0-100) and obstruction class.
- **V1 confidence model (deliberately crude — only what SatCORPS gives us cleanly)**:
  - Cloud fraction >70% → class `cloudy`, `P(unobstructed) = 100 - cloud_fraction`
  - Cloud fraction <20% AND no sun-glint geometry → class `clear`, `P(unobstructed) = 100 - cloud_fraction`
  - Sun-glint risk (see formula below) → class `sun-glint risk`, `P(unobstructed) = max(0, 60 - cloud_fraction)`
  - Mid (20-70%) → class `cloudy`, `P(unobstructed) = 100 - cloud_fraction`
  - Thin cirrus / haze / snow-IR detection: **explicitly out of V1**. They need a real classifier; cut.
- **Sun-glint formula**: compute angular separation between (a) the specular reflection vector of the sun off Earth's surface at the target lat/lon at pass time, and (b) the ISS-to-target nadir vector. If separation < 25° AND the surface beneath is water (use a static land/sea mask), flag `sun-glint risk`. Pre-compute the land/sea mask at startup; one-time download.
- **V1 calibration is log-only.** The frontend writes `Shoot`/`Skip`/`rate(1-5)` events to a calibration log via the Worker endpoint (see Component 6). The generator reads recent calibration entries and includes them in the next tick's debug log, but does NOT yet retune thresholds. Threshold tuning is V2.

**3. Target database** (`targets.json`, in repo)
- Schema:
  ```json
  {
    "id": "tokyo-night",
    "name": "Tokyo at night",
    "geom": { "type": "point", "lat": 35.68, "lon": 139.69 },
    "priority": 5,
    "regime": "night",
    "notes": "Wide lens, expect city sprawl + Tokyo Bay outline"
  }
  ```
- Pre-populate ~50 *static* targets pre-launch: hometown, family/friends' cities, named geographic features (Lake Baikal, Grand Canyon, Patagonia, fjords, the Sahara, the Andes, the Japanese coastline), plus a hand-picked list of *named* volcanoes (Etna, Stromboli, Kīlauea, Sakurajima, Mt. Fuji) — all coordinates known and static.
- **Dynamic-event feeds (active volcanoes by latest USGS / hurricane basins by NHC / aurora oval by NOAA SWPC) are V2.** Each is a separate adapter with its own auth, format, and failure mode; not weekend work. Defer.
- **Target list is frozen at launch −1 week.** The "edit during mission via git push" idea is dropped — open question #2 in the previous draft contradicted itself. If you want a target added in flight, it requires the ground-side support contact to run the generator with an updated `targets.json` and re-deploy. Keeps the orbit-side workflow read-only.

**4. Scoring engine** (`generator/score.py`)
- All values are 0-100 scale (not 0-1) end to end.
- Per candidate pass:
  - `regime_fit` ∈ {100 if pass regime matches target preference, 70 if target is `any` on a terminator pass, 30 if mismatch}
  - `nadir_proximity` — great-circle distance from target to closest-approach point on the ground track, in km. Linear falloff:
    - 0 km → 100, 250 km → 50, 500 km → 0, clamped
    - 500 km horizon = approximate camera-friendly viewing horizon from ISS at 410 km altitude
  - `priority_weight` = `(target.priority / 5) × 100`
  - `score = (P_unobstructed × regime_fit × nadir_proximity × priority_weight) / 1_000_000` → 0-100
- Output:
  - `top5.json` — top 5 in next 90 min for the queue cards
  - `passes.json` — top 25 in next 6h for the map view
  - `score_components` field in each entry exposes the four sub-scores. **Not shown in UI in V1** (drop the "why this card scored" detail; can be added later if you want it).

**5. Frontend** (static, MapLibre, total payload ~150-300 KB once map tiles + cloud overlay tile load — *not* "KB-scale," reviewer was right to push back)
- **Discipline (per /plan-eng-review)**:
  - **UTC end-to-end.** All timestamps in JSON are ISO 8601 with `Z` suffix. Frontend uses `Intl.DateTimeFormat('en-US', { timeZone: 'UTC' })`. Cards explicitly render `14:23 UTC`. Unit test asserts the rendered string ends with `UTC` so this can never silently regress. UTC also applies in filenames, log entries, health-check comparisons, target windows, and any time-based computation.
  - **Manifest-driven loading.** Frontend reads `manifest.json` first (cache-busted). Every other artifact is loaded from the version-tagged path inside the manifest. Single source of truth; no mixed-version reads.
  - **Live ISS dot from polynomial.** Generator emits `iss_polynomial.json` (5th-order polynomial fit of next-30-min ISS lat/lon vs time UTC). Frontend evaluates the polynomial every 1s for smooth motion between 30-min ticks. ~100 numbers, < 1 KB.
  - **Banner thresholds shift** with the 30-min tick: green if `manifest.generated_at` < 40 min ago, yellow at 40-60 min, red at >60 min.
- **Primary view: Shot queue cards (top 5)**
  - Each card:
    - Target name (no thumbnail in V1 — pre-rendered map images add a static-asset pipeline that isn't worth a weekend)
    - Countdown to **closest approach** (not end-of-pass): `In 23 min`, `Now (4 min remaining)`, etc.
    - `P(unobstructed): 87` (0-100 scale, no `%` to keep it ambiguous-free)
    - Obstruction class: `clear` / `cloudy` / `sun-glint risk`
    - Regime: `Night` / `Day` / `Terminator`
    - One-line note from target DB
    - Buttons: **`Shoot`** / **`Skip`** (two only — `Log later` cut, opportunistic photography needs a snap decision, not a deferral)
  - Auto-refresh every 60s. No pull-to-refresh (drop scope).
- **Secondary view: Map** (toggle from queue, default tab is queue)
  - ISS dot, ground track (next 2 orbits)
  - Targets as colored points (color = score, gradient red→green)
  - Cloud overlay: a single global PNG tile from the cached SatCORPS hour, served from R2; no per-zoom retiling in V1
  - Time toggle: `Now` / `+90 min` (V1); full timeline slider is V2
- **Footer status banner**
  - Green: `Last updated 2 min ago`
  - Yellow: `Last updated 12 min ago — generator is slow`
  - Red: `STALE — last updated 4h ago — values may be wrong`
- **Calibration log**
  - Tapping `Shoot` or `Skip` on a card POSTs `{target_id, pass_time, action, score_at_time}` to `/api/log` (Cloudflare Worker → writes JSONL to a separate R2 bucket: `r2:orbit-calib`).
  - When you actually take a shot you can rate it later (1-5 + obstruction-observed dropdown) via a `/log` page that lists recent unrated shoots.
  - Generator on the Mac periodically pulls the calibration log via R2 read API and includes recent entries in its debug log. **No threshold retuning in V1** — that's V2 ML work.
  - **Privacy note**: the Worker endpoint should require a shared secret in a header (you set it in localStorage once at first visit) so randoms on the open web can't pollute your calibration log with junk.

**6. Cloudflare Worker — `/api/log` ingest**
- Tiny Worker (one file, ~50 lines) bound to map.astroanil.dev/api/log
- Accepts POSTs from the frontend; verifies the shared secret in the `X-Calib-Token` header against a Worker secret (env var); writes the JSON line to `r2:orbit-calib/log.jsonl` (append-only).
- Also exposes `GET /api/health` that returns `{ ok: true, last_run: <reads status.json from R2> }` — UptimeRobot pings this every 5 min for staleness alerts.
- Free tier: 100k Worker requests/day. Calibration POSTs are tens per day max; health checks are ~290/day. Headroom is enormous.
- This is the *only* dynamic endpoint in the system. Everything else is static R2.

### Reliability story (the 8-month uptime)

- **launchd plist** with `KeepAlive=true` keeps the daemon alive on the Mac
- **daemon.py stall watchdog** (OpenClaw pattern): any subprocess hung > 10 min gets killed and restarted. The OpenClaw subprocess-wedge mode applies here directly.
- **Status JSON** at `https://map.astroanil.dev/status.json` exposes `last_successful_tick`, per-step latencies, last-fetched-TLE epoch, last-fetched-cloud-composite hour, generator process uptime
- **External monitor**: **UptimeRobot free tier** (50 monitors, 5-min checks, free email/SMS/webhook alerts). HTTP check on `https://map.astroanil.dev/api/health` every 5 min; alert if `last_run` is more than 30 min old or the request fails. Webhook fires into your existing OpenClaw notification pipeline so all uptime alerts land in the same place.
- **macOS auto-update + FileVault hazard**:
  - Disable automatic macOS *major* version upgrades (System Settings → Software Update → uncheck "Install macOS updates automatically"); allow security-only updates only
  - If FileVault is enabled, configure auto-unlock at boot (`fdesetup authrestart` after kernel updates) or document a recovery process for the ground-side support contact
  - launchd plist runs as a user agent that requires user login — acceptable on a headless Mac as long as auto-login is enabled and the user account is the only one
  - Test reboot recovery as part of the 2-week soak
- **Graceful staleness**: site never goes 500. Stale data still renders. Frontend treats any `last_run` older than 30 min as `STALE` and visually demotes scores to grey.
- **Recovery ladder**:
  - Generator throws → retry 3× with exponential backoff (max 1h)
  - Daemon dies → launchd restart (KeepAlive)
  - Mac reboots → launchd auto-starts daemon
  - Cloud composite fetch fails → fall back to last-known-good cached composite with `STALE` flag
  - TLE fetch fails → use cached TLE per the freshness policy in Component 1
  - R2 sync fails → retry; alert at 30 min of consecutive failures
- **Pre-launch soak**: 2-week unattended run on the actual Mac you'll leave behind. Tail logs daily. Inject failures (kill the network, kill the daemon, expire a TLE manually, simulate auth failure, force reboot). Verify graceful behavior + UptimeRobot alerts fire correctly.
- **Ground-side support runbook**: a one-page doc covering "if Mac is silent for 24h, do X." Includes SSH-in (or in-person reach), launchd state checks, disk-full check, Earthdata token expiry check, restart procedure. The named ground-side support person should be someone who can physically reach the Mac if needed.

### Deployment

- **Host**: **Cloudflare R2** (object storage) + Cloudflare Workers (the `/api/log` and `/api/health` endpoints). **Not Cloudflare Pages.** Pages free tier caps at 500 builds/month; a 10-min tick = 4,320 deploys/month, blowing the cap on day 4. R2 has no build-step counter — `rclone sync` overwrites changed objects without triggering anything.
- **Pipeline**: Mac generator → writes JSON + tile assets to `out/` → `rclone sync out/ r2:map-astroanil-dev/` → R2 serves via custom domain map.astroanil.dev
- **Domain**: map.astroanil.dev (Cloudflare DNS, R2 custom domain binding; certs handled by Cloudflare)
- **One-time setup** (~30 min, pre-launch):
  - Cloudflare account + R2 enabled (free tier)
  - Create R2 bucket `map-astroanil-dev`; bind to custom domain `map.astroanil.dev`
  - Create R2 bucket `orbit-calib` (private, for calibration log)
  - Deploy Worker for `/api/log` and `/api/health` (one wrangler.toml, one index.ts)
  - Generate R2 API tokens; store in `~/.config/orbit-photo-director/credentials.json`
  - Generate calibration shared secret; set as Worker env var; copy to your browser localStorage on first visit
- **Repo**: a single git repo (private GitHub or local) for the *code* — `targets.json`, generator, Worker, frontend assets. The *data* (passes.json, status.json, etc.) is never committed; it lives only on the Mac and in R2.

### V2 forward prediction (deferred, but designed for)

V1's data model is forward-compatible. V2 adds:
- A forecast adapter using NOAA NOMADS GFS (cloud cover at +1h, +3h, +6h, +12h grid)
- A timeline slider on the frontend that scrubs the same data structure across time
- A second confidence band: forecast confidence falls off with horizon
- Threshold tuning from the V1 calibration log (Brier score on observed `clear`/`cloudy` outcome vs. predicted P(unobstructed); retune cloud-fraction cutoffs to minimize Brier score across the labeled dataset)
- The thin-cirrus / haze / snow-IR obstruction classifier (deferred from V1)
- Dynamic-event feeds (USGS volcanoes, NHC hurricanes, NOAA SWPC aurora oval)

V2 is ~1-2 weekends of generator-side work plus a frontend slider. **Ship path**: the *Mac* is on Earth — it is the ground-side support person (or you, when you have unmetered home internet) who runs `rclone sync` after a code update. There is no "push from orbit" step; that phrasing in the prior draft was confused. V2 ships either pre-launch (if scope allows), mid-mission (ground-side support deploys it), or post-mission (just for fun).

## Success Criteria

- **Pre-launch**: V1 ships with shot queue, target DB pre-populated (~50 targets), cloud overlay, calibration logging via Worker endpoint, STALE banner, OpenClaw-pattern reliability harness, R2 deploy pipeline
- **Pre-launch**: 2-week unattended soak test passes — zero human interventions required, all injected failures (network kill, daemon kill, TLE expiry, auth failure, reboot) recover gracefully and trigger the right alerts
- **In orbit, week 1**: tool used at least once per orbital day; queue surfaces at least one shot per pass you'd consider taking
- **In orbit, month 2**: calibration log has ≥100 labeled entries (`shoot` + `rate 1-5` + observed obstruction class). This is the V2 training set.
- **In orbit, month 4**: assess Brier score on V1 predictions vs. observed outcomes from the calibration log. Target: Brier < 0.18 (random = 0.25, perfect = 0.0). If achieved without retuning, V1 cloud model is fine; if not, V2 retuning has clear leverage.
