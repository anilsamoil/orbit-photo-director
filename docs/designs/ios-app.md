## Problem Statement

SNAP is a website. In orbit the link drops for minutes to hours. The site already boots from a saved copy, caches a few map tiles and runs its own orbit math for the ISS dot. Four limits remain that no change to a website removes:

1. A website cannot set an alert by itself. Today's workaround is a calendar file the operator exports by hand.
2. A website cannot fetch fresh data in the background when the link returns.
3. A website's storage is small and the browser may clear it. Offline, the map has the world view (85 tiles per layer), a few tiles near the top three targets, and a few hundred recently viewed tiles kept for about a week.
4. The website's sign-in cookie can expire while the device is offline. The app must distinguish credential rejection from a network outage and keep the last authorized plan readable offline.

The ISS position must update without a network connection using onboard orbit data.

The job: put SNAP on the iPad and iPhone as an app that keeps working when the link is gone, without forking the website that ships changes every week.

## What Makes This Cool

The inverted ISS tracker becomes self-reliant. The iPad carries the plan, the planet and the orbit. The link only improves what is already there.

The idea that came out of the second opinion: treat each data update as a plan pack, a complete package that works alone. Several days of targets, the Earth map, orbit data and pre-set alerts. Once the pack is trustworthy, new things open up: a Lock Screen countdown to the next target, crew iPads passing the freshest pack to each other over station Wi-Fi, the ISS view as a viewfinder with Shoot and Skip.

## Constraints

- The orbit devices have no local debugging connection. A fix reaches orbit as a new App Store build downloaded over the station link.
- The web frontend ships weekly. Four pull requests merged on the day this was written. The app must not become a second codebase.
- The main checkout runs the live generator daemon. Release 1 changes nothing in `generator/`.
- The build Mac has no Xcode and no code-signing identity (checked 2026-11-15). It has Command Line Tools 27.0 with Swift 6.4. `swift build` works. `swift test` works with Swift Testing. `import XCTest` does not resolve.
- The GitHub repository is public, so GitHub-hosted macOS runners cost nothing.
- Every path except `/api/profiles` is behind Cloudflare Access with Google sign-in or a one-time PIN. The Worker requires a human identity (`sub` and `email`, `worker/src/calibration-auth.ts:56`) and same-origin writes (`:95`). Google refuses its sign-in inside an embedded web view.
- iOS holds at most 64 pending local alerts per app and promises no background time.
- A TestFlight build stops opening 90 days after upload.
- The orbit devices are an 11-inch iPad Pro with M4 on iPadOS 26.6.2 and an iPhone 17 Pro on iOS 26.6.1. Both are managed by NASA: every app needs NASA's approval before it is installed, and TestFlight will not be approved. Storage and download size are not constraints.
- Map tiles have owners. Esri imagery and labels may not be redistributed in an app bundle without a licence decision.

## Premises

1. The first build is today's SNAP made signal-proof. No new features until that works.
2. With no signal, the order of importance is: (a) map and live ISS position always draw, (b) the shot queue stays useful for days, not hours, (c) alerts, (d) no sign-in lockouts, and shots log offline.
   - Corrected (c). While open, SNAP pre-sets alerts for the next targets up to the iOS limit and shows how far ahead they reach. Background refresh extends a stored schedule while its scheduling inputs still match, including after a verified scores-only change. If that schedule reaches its end, the runout alert asks the user to open SNAP. D-5 governs coverage when scheduling inputs change.
3. NASA manages both orbit devices and must approve every app. NASA installs SNAP from the App Store at G7. TestFlight is limited to ground testing.
4. Signed builds require an active Apple Developer Program membership and the owner setup in [OWNER_STEPS.md](../ios/OWNER_STEPS.md).
5. The website stays in service. Its personal data follows the shared grant and deletion rules in D-6. The operator uses the app first. Crewmates get it once it has held up.

## Recommended Approach

Release 1 is an app that carries the existing SNAP screens. Native code replaces the network underneath them. After release 1, native pieces are added one at a time, each for a measured reason.

Decisions, one line each with the reason:

- **D-1 Host.** Capacitor by default. Gate G1 confirms or replaces it in two steps: a proof on a simulator (W-02, no account needed), then the same proof signed and installed on a ground device (W-03) after G0 and ground setup. Use internal TestFlight or a W-74 ad hoc build on a registered ground device. Host-dependent packages (W-11, W-32, W-41) start after the simulator step, at risk until the device step passes; changing host after them costs their bridge code, about a week. Reason: the implementer knows it and it handles web-view hosting; the proof exists because hashing, map workers and the two map renderers must all work from a local origin before anything depends on them.
- **D-2 One frontend.** A small seam, `frontend/src/host/`, is the only place that knows whether SNAP runs in a browser or in the app. The browser side applies W-20's shared account, artifact, and profile-write contracts. Browser Remind keeps Add to Calendar and the download fallback through a short-lived handoff that the Worker checks against current authorization at delivery. Both hosts use the same frontend. [Browser calendar handoff](../ios/ARCHITECTURE.md#browser-calendar-selections)
- **D-3 Native owns durable state.** Installed plans, the profile binding, unsent logs, and the credential live in native storage. The active account owns its installed plans, mirrored web caches, and alert plan. Switching accounts or signing out hides the outgoing account's data and clears its pending and delivered alerts, even offline. When shared-profile erasure advances the data revision, close old private reads and replace any affected shell document before serving the clean revision. The baseline assets are shared. Web storage remains a cache because it can be cleared and has a different origin inside an app.
- **D-4 A queue that lasts days.** To build `top5`, the generator ranks rows whose closest approach falls before the generator tick plus 90 minutes and keeps up to five by score. That cutoff allows past rows, including legacy launch passes that rank high enough. The reservation step can insert a missing legacy launch pass only if its closest approach is strictly after the tick and before the cutoff, replacing the lowest-scoring row when full (`generator/main.py:1435-1450`). The published Upcoming artifact has a limit of ten rows (`generator/config.py:25-27`). The published Queue ground picks expire within 90 minutes of the last sync. The device therefore computes passes from now to seven days ahead for every target, from the published target list, the personal targets and the newest orbit data, with one shared orbit ephemeris for all targets (the dropped-pin finder propagates per pin and is far too slow for this). Filter published and device ground candidates separately for the current view before matching. Match eligible ground passes for the same target when their closest approaches are within five minutes. In Queue, keep the device pass if it alone is eligible for **Shoot**. Keep the published scored pass for other Queue matches and for Upcoming matches. Queue shares five slots across the next 90 minutes. Ground candidates must have a strictly future closest approach at display time. In **All**, up to two eligible launch cards come first, selected from the separate schema 2 launch feed. The eligible ground rows actually present in `top5`, ordered by score, then the remaining device passes by time, fill the remaining slots. **Mine** makes all five slots available to personal ground passes. **Launches** shows up to two eligible launch cards. Upcoming lists published picks, then device passes by time. Device passes carry geometry, lighting and the three non-cloud score factors, are labelled as device-computed, and show no cloud number. A device pass is marked approximate in its card and its notification when its closest-approach time minus the epoch used exceeds the age validated by W-12. W-12 tests multiple prediction ages across a reboost and counts missed and extra passes alongside the 60-second limit for matched passes. If no age passes, mark every device pass approximate. When newer orbit data is installed, the next queue recalculates the passes and their markers. D-5 governs pending notifications during the switch. In the app, an authorized **Shoot** on a qualifying device-computed Queue card works offline even after the published manifest goes stale. The device queue is on in the app only in release 1 and survives a Mac outage without changes to the live generator or extra bytes over the link. [Queue contract](../ios/ARCHITECTURE.md#the-queue-between-syncs)
- **D-5 Alerts.** While open, the web side builds an alert plan. Native code stores it, schedules up to the iOS limit and shows "Alerts set through ...". Remind on an individual pass takes priority over automatic alerts and works outside the automatic target filter. A second tap cancels that pass across replanning. A closed-app refresh preserves the schedule, coverage and runout alert when it can verify that scheduling inputs are identical, even when numeric scores change. A score change across a published Queue cutoff can change those inputs. All and Launches include eligible capture windows from the verified schema 3 catalog used by Upcoming. A lease renewal with equivalent scheduling facts preserves pending ground alerts and launch alerts that still meet both deadlines. When ground scheduling inputs stay verified and equivalent, a launch-only feed switch, timing change or omission preserves ground requests with their original IDs and fire times. Native code clears only affected launch requests before activation and reconciles coverage from the retained requests. An omission pauses the launch alert. A verified eligible capture for the same ID can restore it on the next plan submission. Durable withdrawal is deferred until the provider exposes an authoritative disposition for that event. If ground inputs change or their equivalence cannot be verified, native code clears the old plan and its coverage before activating the new inputs. If coverage is interrupted while the app is closed, it uses the runout slot for a generic coverage-paused notice. The next open computes the replacement alert plan. The runout alert asks the user to open SNAP at the end of coverage. Published-pass alerts carry verified contribution IDs from the guarded publication. When a shared-profile contributor's target data is erased, native cleanup uses those IDs to remove affected delivered alerts even after a target replacement or artifact expiry. Delivered alerts for independently attributable targets stay in Notification Center. The contract accounts for the 64-alert limit and the lack of guaranteed background time. [Alert scheduling contract](../ios/ARCHITECTURE.md#alerts)
- **D-6 Sign-in and profiles.** SNAP opens without sign-in (D-12). Native-first Apple and Google accounts can enroll and receive their own profile without operator approval, subject to the deletion fence. Before the first native binding of a migrated website generation or any other existing website generation with private data or grants, including a replacement opened on the website, the operator verifies the holder independently. The holder confirms that exact attested attempt with their own recovery credential. Bind approval to the verified subject, generation, installation key, candidate credential and both deletion verifiers, and recheck the approval requirement and consume the approval in the fenced commit. If independent proof is unavailable, keep the generation on the website. Google enrollment uses the system browser sheet and a separate Cloudflare Access application. Apple enrollment verifies the single-use session nonce in both the incoming identity token and the token returned by the code exchange before granting access. The Worker retains encrypted credentials for potentially live authorizations. Both choices issue a native credential that the Worker accepts only with a fresh assertion from the enrolled App Attest key. The Worker projects each website and device manifest and authorizes personal artifact reads against current generations, grants, and deletion state. On each website host, a data revision advance also closes the surviving grantee’s earlier reads, rendered views and cache writes. A profile outside the generator roster uses the shared plan, authenticated personal-target sync, and geometry-only passes offline. Profile reads and generator snapshots use one committed revision of the targets and hidden curated entries. At cutover, both website hosts and iOS defer CSV file and paste imports and unreviewed JSON imports. Individual adds remain available. Browser JSON Replace submits the exact approved target list and removed-curated state in one conditional PUT. The bootstrap CLI applies a saved target edit against the revision the operator reviewed. The website email allowlist stays outside `/d/*`. Rate limits, quotas, and per-device revocation control abuse. Sign-out returns to the baseline and retains that account's pending logs for its next sign-in. Verified Apple consent withdrawal closes the affected Worker authorization and signs out the account locally, clearing its pending and delivered alerts. Its unsent logs stay available for the same account's next sign-in unless SNAP confirms deletion. Deletion blocks profile access at acceptance and purges published copies, generator Mac copies and the account's shared-profile contributions before completion, subject to the published legal retention policy. Cleanup covers affected operator-controlled target import sources, and the bootstrap CLI blocks retired source approvals. Fresh enrollment after deletion creates a new account and profile generation. Other devices clear the account and alerts when they learn of deletion. For in-app deletion of an Apple account, completion requires provider confirmation for every potentially live authorization and unresolved exchange. At first native enrollment for either provider, the account holder saves a primary deletion recovery key and a separate spare code outside SNAP and shared-device access and binds a discoverable, deletion-only WebAuthn credential. The holder can choose a USB-C or NFC FIDO2 security key or an independently bound software credential such as a synced passkey held outside the shared device's credential store and verified under the holder's control. Both options must pass the same restore and shared-iPad fixtures, including recovery while the sign-in provider is unavailable. Ordinary deletion requires the primary key in addition to the session and installation proof. Signed-out Settings accepts the saved primary key on a clean installation after device loss or consent withdrawal. With both saved secrets lost, **Use my recovery credential** accepts a fresh user-verified assertion from the already-bound credential and fresh App Attest proof, including after erasing and restoring the original device or restoring to a replacement. This route authorizes only deletion and requires no fresh provider sign-in. Settings requires holder proof to change either secret. Apple enrollment asks for no additional email. After enrollment, the holder can opt in to a verified independent mailbox. A fresh code from that inbox and the separately saved spare code authorize recovery on a clean installation if the primary key is lost. The retained-installation path also requires local user presence, its deletion credential and a fresh App Attest assertion. Sign-out or account handoff retires the outgoing installation proof. SNAP cleanup starts at acceptance. The separate provider revocation step can use retained credentials or fresh Apple authorization where available. After SNAP cleanup, the receipt reports manual action if an Apple authorization cannot be confirmed. - **D-6a Logs saved exactly once.** The current Worker keys dedupe by arrival month so a lost acknowledgment can cause a later-month retry to write a second record. W-20 adopts retained monthly records into a reservation shared by the website and device routes. The dedupe reservation uses the authorized profile and raw dedupe key. A native append without a dedupe key reserves a record using its durable per-action token scoped to the acting account, destination profile and data revision. Each reservation preserves the original payload, first receipt time, and monthly destination. New logical monthly destinations encode the tuple without ambiguity. Physical object keys are opaque. Tracked multipart operations give cleanup a terminal result before erasure. Every retry completes or verifies the reserved write before acknowledging it. Two profiles using the same key get separate records. Two eligible accounts using the same key for a shared profile dedupe while its canonical reservation survives. After erasure removes that reservation, a fresh action on the updated profile can create a new record with the same key. The native outbox keeps each entry with its original account, selected profile, and data revision. It holds earlier-revision entries outside automatic drain so a fresh same-key action can upload independently. Each browser origin and native installation caps held data across accounts and profiles, reserves room for fresh writes and keeps the original seven-day expiry across restores. Shot logs also carry verified target contribution provenance. Erasure removes the contributed pass details from committed, pending, rejected and revision-held records, including target-derived keys, while preserving the surviving author's independent action data. ## Success Criteria

- **Gates G2 (simulator) and G3 (ground device).** Cold-launch offline, verify Earth draws and the ISS prediction moves, and receive an alert while locked. With the published Queue expired, tap **Shoot** on a qualifying device-computed Queue card and confirm the shot survives an offline restart and uploads once on reconnect.
- **Updates keep state:** a new build installed over the previous one, with an installed plan and unsent log entries present, keeps the credential, the plan, the outbox, the kept tiles and the settings, and the queued entries upload once. This step is part of G2 and of the G3 checklist.
- **Signed out.** A fresh install with no account, no network and demo mode off shows baseline targets and device-computed passes. Map and ISS view draw Earth and use the same moving ISS prediction. Repeat with the network blocked after signing out and confirm the outgoing account's data is absent.
- **In orbit, first two weeks.** No sign-in prompt after enrollment. The map draws from world view through the baseline's deepest zoom. Queue shows a pass when a target has a qualifying pass in the next 90 minutes. Upcoming shows qualifying later passes through the seven-day prediction horizon. Each logged shot reaches the server exactly once.
- **Before orbit:** the ground tester passes G3 on the candidate before App Review submission. At G6 the tester installs the live App Store release over the installed TestFlight or W-74 ground build and verifies state and no expiry. After G3 and G6, NASA approves and installs from that listing at G7.
- **Ground builds:** the tester installs replacements before TestFlight or ad hoc provisioning expires.
- **For the website:** the frontend suite, `typecheck` and `verify-map-pins.mjs` stay green on every pull request that touches `frontend/`; CI runs the first two, and the implementer runs the third and attaches its output. The browser contract tests cover the seam, and W-20 verifies the shared authorization policy on both hosts.

## Distribution Plan

- **Channel:** the App Store, preferably unlisted, with a public listing if Apple declines the unlisted request. NASA installs the approved build on the orbit devices (G7); crewmates later use the same listing and approval (W-73). Ground testing uses TestFlight, with W-74 ad hoc delivery as the fallback.
- **Pipeline:** GitHub Actions on a hosted macOS runner. Pull requests build and test on a simulator with no secrets. On a clean hosted runner, Xcode uses automatic provisioning and Apple Distribution signing. The App Store Connect API key authenticates Xcode. Release candidates run from `main` in the protected release environment and upload to App Store Connect.
- **Cadence:** a new build whenever app code changes. TestFlight refresh builds for the ground tester at least every 45 days while ground testing continues.
- **Size.** The project sets no download-size limit. Large downloads run overnight. The baseline map at zoom 0 to 5 is estimated at about 68 MB (2,730 tiles at about 25 KB). W-40 measures its size. W-70 records preapproval download and install estimates for iPhone and iPad, then reports update measurements with the channel and predecessor when available. The first App Store version has no App Store predecessor. The separate 512 MiB tile-store cap controls downloaded tiles on disk.
- **Fallback:** the website.

### R2-3 — clarity (blocking)

**Problem**

> The rule that marks device passes approximate does not say what the 48 hours are measured from. W-12 ('a device pass from orbit data more than 48 hours old') and ARCHITECTURE.md repeat the same wording. The banner threshold it borrows measures now minus the orbit data's epoch for the live track (frontend/src/banner.ts:88-92). For a future pass, the matching measure is closest-approach time minus epoch. The natural reading is the data's age when the pass is computed. Under that reading, a day-6 pass computed from data one hour old is propagated about 6 x 24 + 1 = 145 hours, about three times the threshold (145 / 48 = 3.0), yet it is shown and alerted unmarked. That is the seven-days-ahead case R1-12 raised, and it is what W-12's accuracy check measures.

**Remedy**

> Define the age as the pass's closest-approach time minus the epoch of the orbit data used, in D-4, W-12 and ARCHITECTURE.md. Say that the mark is recomputed when newer orbit data is installed. If age at computation is intended, say so and give the reason.
